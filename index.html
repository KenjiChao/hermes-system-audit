01

先處理什麼

先修已重現的錯誤與維護流程，再校正知識與設定，最後才清空間。

優先修正

先處理會製造錯誤的修補

中文轉換會改壞路徑／網址；掃描例外規則過寬；Patch 套用失敗可能留下衝突。三者都已在隔離環境重現，不只是推測。

建議做法先補行為測試、修正或退役對應修補，再處理整套套用流程。全部保留備份，不直接在運行中的安裝上試錯。

優先

讓操作知識回到單一版本

維護 Skill 和常駐記憶仍留有已過時的絕對規則。例如，『config set 不能設定陣列』已不符合目前程式行為。錯誤知識以操作指令的形式被反覆載入，比單純檔案太多更值得先處理。

建議做法先更新 Hermes 維護相關 Skill，再刪去常駐記憶內重複的操作教學；歷史案例保留在參考文件，不再當成現行指令。

需決策

確認換模型的範圍

目前話題使用 gpt-6-astra／OpenAI Codex，但全域預設仍是 Opus 4.8／OpenRouter。話題切換不代表所有新聊天、排程與輔助任務都一起切換。

建議做法先選定全域模型與付費管道，再核對話題覆寫與排程的模型快照；這次沒有代為切換。

需決策

收斂破壞性操作的永久授權

部分高風險指令類別已有永久授權。這不等於所有防護關閉，但模型一旦判斷錯誤，可能造成的影響會比較大。具體授權項目不公開。

建議做法保留日常開發需要的便利性，個別檢視刪除、重設與服務生命週期操作，不要全部關閉或全部放行。

02

系統與設定

有些是確定需要整理的設定，有些只是診斷警告，不能混為一談。

已驗證

程式版本是新的，服務也已載入

版本檢查顯示核心為 0.21.3；執行中服務回報的 code SHA 與安裝目錄 HEAD 相同。不是『更新了檔案，服務卻還跑舊程式』。

查看查證依據

hermes --version、Git reflog、gateway_state 的 code_sha 交叉核對。

建議修正

背景服務定義落後於目前程式

服務雖然正常運行，但安裝中的 launchd 定義和目前官方產生器不同。特別是 KeepAlive 還是舊的無條件重啟方式，目前產生器已區分正常結束與異常結束。

建議做法在可中斷工作的維護時段，用官方支援的服務管理流程更新；不要再另寫延遲重啟腳本。

查看查證依據

gateway status 警告，加上 installed／generated plist 的結構比較；沒有觀察到當下正在重啟循環。

建議修正

工作回合上限有兩份相反設定

Doctor 檢出環境檔的回合上限為 90，設定檔則為 300。這是舊環境變數殘留，不能只看 YAML 就認為實際一定會用 300。

建議做法清除舊的非機密環境覆寫，再驗證新代理實際使用的上限。不要用不斷提高上限掩蓋流程問題。

非故障

不能只看一個 false 就說防護關了

雖然設定中的 hard_stop_enabled 是 false，但實際解析結果是 Telegram 與 cron 的停止防護仍然開啟。程式的非互動平台預設值會補上保護。

查看查證依據

直接呼叫目前設定解析器：CLI＝false、Telegram＝true、cron＝true。

待整理

憑證與依賴需要局部維護

Doctor 回報一條非目前主聊天管道的直連 API 憑證失效；現用聚合管道與 Gemini 檢查通過。另有瀏覽器及 Web 工具依賴的安全公告，不能直接等同遭到入侵。

建議做法先釐清不用的憑證是否應保留；依賴更新優先跟隨相容的上游 lockfile，不直接對運行中的安裝盲跑 audit fix。

03

Patch 審核

四個 Patch 都能成功套用，而且完整重建了現有的原始碼差異；但『套得上』不等於『功能正確』。

優先修正

標點／繁體轉換會改壞正確路徑

已重現：中文檔名的副檔名分隔點會被轉成全形句號；中文網址路徑也會被轉字，部分 Markdown 連結因此失效。這是輸出層的確定性改寫，不是模型幻覺。

建議做法保留中文標點與繁體偏好，但在轉換前保護網址、路徑、連結目標、程式碼與需忠實引用的原文。不要用刪掉整個功能來掩蓋問題。

查看查證依據

Patch 004。真實 Telegram 格式化函式：/tmp/字幕.srt → /tmp/字幕。srt。未修補上游保留原路徑；ASCII 與程式碼區塊控制組正常。未發送測試訊息。

優先修正

掃描例外放行的範圍太寬

一個原本為避免 Google API 範例誤判的例外規則，會把不應忽略的內容一併從掃描輸入移除。隔離測試中，上游能攔截的測試字串，在本地 Patch 下通過。公開頁不提供繞過細節。

建議做法先確認目前上游是否已解決原本的誤判，再退役該例外或改成精確的結構驗證。不能用寬鬆字串比對跳過整段掃描。

查看查證依據

Patch 002。使用真實掃描函式、無憑證測試字串與未修補上游對照；沒有執行任何測試字串中的命令，也沒有證據顯示已發生入侵。

優先修正

Patch 套用失敗，仍可能留下半套修改

在拋棄式測試資料夾中，現行套用腳本報告失敗後，仍留下合併衝突標記或部分已修改的檔案。停止迴圈並不會撤回先前的寫入。

建議做法先在隔離副本完成整套重播與測試；正式安裝只允許已檢查的套用，遇到漂移就停止。不要在正式原始碼上繼續嘗試三方合併與部分套用。

查看查證依據

原樣執行現行腳本，但 HOME 指向一次性測試環境。兩個失敗案例分別留下衝突標記與部分改動。正式安裝未被拿來故障注入。

可退役／保留

同步委派 Patch 可退役；SRT 支援仍有用途

Patch 003 的 cron 同步委派目的，已由上游以每個工作階段的交付能力處理；舊 Patch 還讀取過時的全域環境標記。相反，Patch 001 的 SRT 文件與媒體支援仍補足上游缺口。

建議做法經批准後退役 003，保留 001 並補測試。這是語意上已被上游取代，不是僅靠反向套用檢查就判定程式碼已合併。

查看查證依據

未修補上游的 cron／API 委派相關測試共 3 項通過；SRT 的 MIME 與交付副檔名集合則仍需要本地變更。

測試結果

原有測試全綠，仍然漏掉六個回歸案例

既有相關測試 162 項全部通過；另外新增的 8 個隔離回歸案例，在本地 Patch 下 6 失敗、2 通過，未修補上游則 8 項全過。現役 Patch 都沒有把測試一起保存。

建議做法把這些行為測試納入修補交付，不再只驗證 git apply 成功。後續修正必須保留正向功能，也守住不該被改動的反向案例。

查看查證依據

均使用目前官方 scripts/run_tests.sh、隔離 HOME 與臨時測試環境。父代理已讀回測試輸出並重新核對重建檔案與正式檔案一致；沒有跑完整上游測試集。

04

Skill 與記憶

精簡的目的，是減少彼此矛盾的指令，而不是讓技能數字變小。

盤點完成

164 份實體 Skill，不是把所有文字常駐載入

去除指向同一實體檔案的別名後，共 164 份 Skill：157 份本地、7 份外部製作流程。七組重複名稱其實是同一檔案的符號連結，不是可直接刪掉的副本。

建議做法保留技能入口與外部專案所有權；優先整理重疊規則。所有 Skill 正文採按需載入，不應把總字數直接當成每次模型呼叫的負擔。

查看查證依據

以已安裝版本的搜尋規則盤點，依 realpath 與 inode 去重。全庫做大小與引用掃描，語意深讀集中在維護相關與大型 Skill，沒有宣稱逐字審完所有內容。

建議拆分

兩個製作 Skill 已超過可編輯上限

make-tech-segment 為 102,982 字元，jkt-asr-pipeline 為 101,455 字元，都超過目前管理工具的 100,000 字元上限；hermes-agent 本身也有 79,180 字元。

建議做法將完整案例與長程序移到參考檔，主 Skill 保留流程選擇與必要規則。這兩個超大檔案屬於外部製作專案，不應由系統清理一併刪改。

查看查證依據

檔案字元量測與目前 skill manager 限制交叉核對。確定有編輯失敗風險，但沒有宣稱當下正在發生無限重試。

建議校正

維護規則互相衝突，Vision 說明也落後

有的 Skill 禁止重新編號 Patch，有的要求重新編號；有的把本地反向套用成功誤當上游已吸收。Vision 又同時存在『永遠走輔助模型』與『原生優先』兩種說明，目前程式是原生優先、輔助路徑備援。

建議做法保留一份版本明確的權威操作流程，其餘入口只連結它。歷史案例要標為歷史，不再用 MUST／NEVER 將舊實作寫成永久限制。

建議修復

有四個確定失效的參考檔連結

確認四個 Skill 內承諾的參考檔不存在；Telegram 格式 Skill 另指向已封存的 TTS Skill。掃描產生的大量候選中，有不少其實是專案路徑或範例，不能全部算成壞連結。

建議做法逐一恢復內容或改指向仍有效的流程；不要把失效連結補成沒有內容的新檔案。先修消費產品、領域經濟、文章翻譯及業配協商的四個已確認引用。

已重現

『不能用 config set 寫陣列』已過時

目前程式已支援解析陣列與物件。實測兩個陣列設定都得到真正的 list，不是字串；但某些動態欄位的 off 仍可能被解析成布林值，不能反過來宣稱所有設定都安全。

建議做法把絕對禁令改成『確認欄位型別，設定後檢查讀回結果』。

查看查證依據

唯讀呼叫 _coerce_config_set_value，沒有寫入正式設定。

建議精簡

常駐記憶幾乎滿載，而且混入操作手冊

MEMORY 為 4,980／5,000 字元，USER 為 2,899／3,000 字元。裡面含過時模型預設、Patch 編號、任務經驗與重複規則；這些會隨每個新聊天一起載入。

建議做法保留穩定的個人偏好與重要環境事實；把任務程序留在對應 Skill。不要單純加大記憶容量，也不要刪除有價值的對話歷史。

05

排程與維護腳本

排程不是全面故障；有真實產出，也有狀態表看不出的交付問題。

優先修正

維護警告被留在本機，沒有送到 Telegram

維護排程設為僅本機交付，但載入的指令又聲稱系統會自動傳送、同時禁止手動傳送。執行紀錄證實：工作完成，交付卻被抑制。即使報告包含需要人工處理的警告，也是如此。

建議做法明確選擇『自動交付到指定話題』或『本機執行、必要時主動通知』其中一種一致契約。不能讓 ok 同時代表執行成功與使用者已收到。

查看查證依據

父代理讀回執行資料庫：completed／suppressed。對照當日實際報告與工具活動，而非只看 last_status。

已驗證

五個排程都啟用，主要內容任務有產出

四個直接引用的 Skill 都存在。日報有新產生的文章與公開成品；Email 與足球任務有工具活動與已交付紀錄。另有一個尚未到首次執行時間的提醒，不能當成失效。

查看查證依據

核對工作設定、執行帳本與最近成品；並未重跑排程或重新審核內容事實品質。三個工作沿用全域 Opus 4.8，另兩個仍固定 GPT-5.6-sol。

需要盤點

超過一百個瀏覽器背景服務累積

審核初始快照有 122 個獨立 browser-harness daemon，部分已持續多日；RSS 加總約 1,871.5 MiB。但共享記憶體可能重複計算，背景化本身也不代表已被遺棄。

建議做法先對照擁有它們的工作階段、連線與最後活動，再清理確認閒置的程序。不要直接殺掉全部瀏覽器。

查看查證依據

以 ps 的確切模組參數計數。頁面驗證新開一個瀏覽器後，父代理再查為 123 個；初始 122 個是建立此頁之前的快照。

建議退役

舊重啟工具與失效服務註冊仍在

有一筆已載入但未運行的舊服務，指向不存在的暫存腳本；還留著固定延遲後重啟，以及『等太久就不管是否閒置而重啟』的工具。這不符合不打斷進行中工作的承諾。

建議做法查清引用後退役失效項目，改用有正式狀態判斷的監管流程。當下沒有證據顯示這筆舊服務正造成重啟循環。

06

真正占空間的是什麼

磁碟臃腫和模型上下文臃腫，是兩件不同的事。

已量測

主要空間在還原快照與對話資料庫

Hermes 資料目錄約占 12.16 GiB，其中檔案還原快照約 5.89 GiB；Doctor 回報對話資料庫邏輯大小約 2.1 GB。Skill 目錄約 0.04 GiB，不是磁碟容量的主要問題。

建議做法先檢視快照是否仍有還原價值；對話資料庫可另外評估離線儲存最佳化。這些資料不會全部塞進每次模型呼叫。

需決策

保留天數不代表正在自動清理

目前快照與對話的 auto_prune 都是關閉的。快照還有『每個專案至少保留一份』規則，因此即使設有容量上限，總量仍可能超出。

建議做法先決定要保留哪些回復能力，再設定清理方式。本輪未刪除任何快照或聊天，也沒有新建清理排程。

07

建議的整理順序

每一輪只改同一類問題，有備份、有驗證，再進下一輪。

第一輪

修補可靠性

修正文字轉換與掃描例外，讓 Patch 套用流程遇到失敗不污染正式安裝；將已重現的案例保存成測試。同步修正維護報告交付，確保失敗能被看見。

第二輪

知識校正

統一維護規則與失效引用，再規劃大型 Skill 的章節搬移。保留所有有用的任務經驗與偏好，不刪減功能來換取漂亮的技能數量。

第三輪

設定與服務

決定全域模型路線；處理環境覆寫、服務定義與永久授權。每項單獨驗證，不把模型切換、服務重啟、資料清理混在同一次操作。

第四輪

容量與依賴

盤點可清理的快照，評估不丟失對話內容的儲存最佳化，再處理相容的依賴更新。

這份審核的界線

這是單次唯讀審核：完成全庫大小／引用盤點、重點維護規則深讀、四個 Patch 的隔離重播與針對性測試、五個排程的交付核對。沒有逐字審完所有 Skill、跑完整上游測試集或做模型幻覺率對照實驗。已證實部分錯誤是輸出後被改壞，但不能斷言所有先前幻覺都由 Hermes 造成。
